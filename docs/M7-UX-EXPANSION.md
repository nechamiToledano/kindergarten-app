## 0. תקציר

המערכת בנויה ומתפקדת מקצה-לקצה (M0–M6): מנוע משחקים גנרי מונע-תוכן, סשן אבחון מלא, שלושה דוחות אנליטיים, ואפליקציית אדמין לניהול תוכן ותמונות. מה שחסר הוא **חוויית משתמש שנראית ומרגישה גמורה** וכמה **יכולות מוצר** שהלקוחה ביקשה בנפרד מהאפיון המקורי: דף בית עם סטטיסטיקה כללית, ניהול ילדים עשיר יותר, מצב משחק חופשי (לא-אבחוני), ותמונות אמיתיות במקום placeholders.

מסמך זה הוא **M7** — לא שינוי ארכיטקטוני, אלא שכבת עיצוב + כמה תוספות נתונים קטנות שיושבות בדיוק על התשתית שכבר קיימת (§3.2, §7, §10.3 ב-HIGH-LEVEL-DESIGN).

**הערה חשובה לגבי מסמך ה-Base44 שצורף כהשראה**: המסמך שהלקוחה שיתפה תיאר מערכת אחרת (Base44) עם ~17 קובצי-משחק נפרדים (MemoryGame.js, LettersGame.js וכו') וישויות עצמאיות. **המערכת שלנו כבר פתרה את זה טוב יותר** — יש 9 סוגי-משחק גנריים (§7 ב-HIGH-LEVEL-DESIGN) שכל תוכן חדש נכנס אליהם כשורה ב-DB, לא כקובץ קוד. לכן בהמשך המסמך אני **ממפה** כל רעיון מה-Base44 (דף בית, מסך ילדים, "משחקים חופשיים") אל הארכיטקטורה הקיימת, ולא מציע לשכפל את המבנה ההוא — זו הייתה נסיגה אדריכלית.

## 1. עקרון-העל של M7

> **התוכן כבר מנוע-נתונים (§3.1). עכשיו גם העיצוב הופך למערכת (design system), לא לעיצוב חד-פעמי למסך.**

כל מה שנבנה כאן חי בשכבה אחת: **`packages/ui`** (שכבר קיימת ומיועדת בדיוק לזה — §5.1, §14.5) מקבלת ~12 רכיבים חדשים משותפים לכל שלוש האפליקציות (`web`, `admin`), ו**טוקני עיצוב** (צבע/מרווח/טיפוגרפיה/תנועה) מוגדרים פעם אחת כמשתני CSS. מסך חדש לא ממציא עיצוב — הוא מרכיב מהרכיבים הקיימים.

## 2. מערכת העיצוב (Design System)

### 2.1 שני מרחבים חזותיים, לא אחד

הארכיטקטורה הקיימת (§11.2) כבר מפרידה בין **מעטפת גננת** (dense, מידעית) ל**משטח משחק לילד** (full-bleed, ללא ניווט). M7 מעצים את ההפרדה הזו ולא מבטל אותה — לילד ולגננת יש צרכים חזותיים הפוכים:

| | מעטפת גננת (Home / ילדים / דוחות) | משטח משחק (Assessment / Games) |
|---|---|---|
| אופי | נקי, קריא, מידעי — "לוח מחוונים יפה" | חגיגי, צבעוני, אנימטיבי — "ילד רוצה לשחק שוב" |
| צפיפות | בינונית (כרטיסים, טבלאות, גרפים) | דלילה מאוד (אלמנט אחד למוקד) |
| תנועה | עדינה (fade/slide, ~150ms) | בולטת (confetti, bounce, ~400-600ms) |
| טיפוגרפיה | Rubik, משקל 400–700 | Rubik, משקל 700–900 בלבד, גדול יותר |

### 2.2 טוקני צבע (מרחיב את `app.css` הקיים, לא מחליף)

הקובץ `apps/web/src/styles/app.css` כבר משתמש במשתנים (`--accent`, `--accent-bg`, `--border`, `--bg`, `--text`, `--text-h`) שהוגדרו כנראה ב-`index.css` — הם נשארים. M7 **מוסיף** טוקנים חדשים, בהשראת הפלטה הסגול/ורוד/כחול שהלקוחה ציינה כדוגמה, אך שמורים כמשתני CSS כדי שיתאימו למצב בהיר/כהה בעתיד:

```css
:root {
  /* קיימים — לא משתנים */
  --accent: #6d28d9;        /* היה קיים; מיושר כאן לסגול חם */
  --accent-bg: #f5f3ff;
  --border: #e5e7eb;
  --bg: #ffffff;
  --text: #6b7280;
  --text-h: #111827;

  /* חדשים ב-M7 */
  --accent-2: #ec4899;               /* ורוד — לגרדיאנטים ולמצב "חגיגה" */
  --accent-3: #38bdf8;               /* כחול בהיר — משני */
  --gradient-hero: linear-gradient(135deg, var(--accent), var(--accent-2));
  --gradient-soft: linear-gradient(135deg, #f5f3ff, #fdf2f8);

  --success: #10b981;   /* כבר בשימוש בדירוגים — הופך לטוקן רשמי */
  --warning: #f59e0b;
  --danger:  #ef4444;

  --radius-sm: 10px;
  --radius-md: 16px;
  --radius-lg: 24px;
  --radius-pill: 999px;

  --shadow-card: 0 1px 3px rgba(17,24,39,.06), 0 8px 24px -8px rgba(109,40,217,.12);
  --shadow-float: 0 12px 32px -12px rgba(109,40,217,.28);

  --dur-fast: 150ms;
  --dur-base: 250ms;
  --dur-celebrate: 550ms;
  --ease-out: cubic-bezier(.16,1,.3,1);
  --ease-bounce: cubic-bezier(.34,1.56,.64,1);
}
```

זה שומר על העיקרון הקיים (CSS logical properties, §11.3) ולא מכניס Tailwind — **החלטה מכוונת**: `apps/web` היום הוא CSS-variables + מחלקות ידניות, נקי ועובד. הכנסת Tailwind באמצע פרויקט בוגר היא עלות מיגרציה בלי תועלת אדריכלית; הרחבת אותה שיטה עצמה עקבית יותר עם §3 (עקרונות הארכיטקטורה — "לא מוסיפים כלים בלי צורך אדריכלי").

### 2.3 טיפוגרפיה

- גופן יחיד: **Rubik** (תמיכה מלאה בעברית, עגול-ידידותי אך קריא, חינמי ב-Google Fonts, טוען היטב ב-Safari על iPad).
- סולם: `--fs-xs` (0.8rem) עד `--fs-hero` (clamp(2rem, 6vw, 3.5rem)) — כבר יש שימוש ב-`clamp()` בקוד הקיים (`.pad`, `.child-instruction`), M7 רק ממסד את זה לסולם רשמי בן 7 צעדים.

### 2.4 רכיבי `packages/ui` חדשים (§14.5 — נכס משותף ל-web ול-admin)

| רכיב | שימוש |
|---|---|
| `StatCard` | אריח סטטיסטיקה בדף הבית ("12 ילדים", "38 סשנים החודש") עם אייקון + מגמה (▲/▼ מול חודש קודם) |
| `Avatar` | תמונת ילד (מ-R2 דרך `StoragePort` הקיים) או ראשי-תיבות על רקע צבע-נגזר-מהשם |
| `ProgressRing` | טבעת אחוזים — לדף הבית ("62% מהילדים אובחנו החודש") ולדוח התקדמות |
| `Sparkline` | קו מגמה זעיר בתוך `StatCard` (Recharts כבר תלות קיימת — §11.1) |
| `EmptyState` | מצב "אין ילדים עדיין" / "אין תוצאות" — עם איור + כפתור פעולה, לא טבלה ריקה שקטה |
| `ConfettiBurst` | פרץ קונפטי CSS-בלבד (לא ספרייה) לתשובה נכונה/סיום סשן — מכבד את §3.3 (לא מוסיפים תלות בלי צורך) |
| `MascotBubble` | דמות-מנחה קטנה (SVG אחד, כמה הבעות) שנותנת פידבק קולי-חזותי לילד |
| `SearchInput`, `FilterChips` | מסך ילדים — חיפוש + סינון לפי טווח גיל |
| `Toast` | אישורי שמירה ("הילד נוסף בהצלחה") |
| `PageHeader` | כותרת עמוד אחידה (כותרת + תת-כותרת + כפתור פעולה ראשי) — מחליף את החזרה הידנית של `roster-head` בכל מסך |

כל הרכיבים **RTL-aware מלידה** (עקרון §11.3 שכבר קיים ב-`packages/ui`), בלי תלות חיצונית פרט למה שכבר מותקן (React, Recharts).

### 2.5 תנועה (Motion)

**החלטה**: לא Framer Motion. הקוד הקיים "שומר על משטח תלויות קטן" באופן מודע (M3/M4/M5 בתיעוד — "kept the slice's dependency surface small"). CSS transitions + `@keyframes` מכסים את כל מה שנדרש כאן: fade-in של כרטיסים, bounce של כפתור נכון, קונפטי. אם בעתיד ייבנו אנימציות מסלול מורכבות (page transitions בין ראוטים) — זה הרגע לשקול מחדש, לא לפני.

## 3. מסכים חדשים ומורחבים

### 3.1 Home — דף בית חדש (לא קיים היום)

היום `App.tsx` קופץ ישר מלוגין לרשימת ילדים (`RosterScreen`). M7 מכניס מסך בית בין השניים.

**תוכן:**
1. **שורת סטטיסטיקה כללית** (4 × `StatCard`): מספר ילדים בגן · סשנים השבוע · % ילדים שאובחנו החודש · תחום הכי "בקושי" חוצה-גן החודש (משיכה ישירה מ-`PatternsReport` הקיים — §12).
2. **4 כפתורי פעולה מהירה** (כרטיסי גרדיאנט גדולים, `--gradient-hero`): "אבחון חדש" · "ילדים" · "משחקים חופשיים" (חדש — §3.3) · "דוחות".
3. **פעילות אחרונה** — 5 הסשנים האחרונים בגן (שם ילד, תחום, תאריך, תג דירוג צבעוני).

**API חדש נדרש**: `GET /reports/kindergarten/summary` במודול `reports` הקיים (§10.1) — מחזיר `{childrenCount, sessionsThisWeek, diagnosedPctThisMonth, topChallengeDomain}`. זו שאילתת-קריאה בלבד על נתונים שכבר קיימים (`PatternsReport` כבר מחשב חוזק/קושי חוצה-ילדים — §12), לכן זה **ריכוז** של לוגיקה קיימת, לא לוגיקה חדשה. tenant-scoped כמו כל endpoint אחר (§9.2, נבדק ב-e2e כמו §15 המחייב).

### 3.2 Children — הרחבת `RosterScreen`

הקיים: רשימה שטוחה + כניסה לסשן. **תוספות:**

- **חיפוש** (`SearchInput`) לפי שם.
- **סינון לפי טווח גיל** (`FilterChips`): "3-4" / "4-5" / "5-6" / "הכל" — מבוסס על `ageGroupAtTime` שכבר נגזר מ-`birthDate` (§10.1, מודול `children`).
- **הוספה/עריכה** ב-דיאלוג (לא ניווט לעמוד נפרד): שם, תאריך לידה (→ קבוצת גיל מחושבת אוטומטית ומוצגת מיד, לא מוזנת ידנית), תמונה (אופציונלי).
- **`Avatar`** ליד כל ילד ברשימה — תמונה שהועלתה או ראשי-תיבות צבעוניים.
- **מחיקה רכה** עם דיאלוג אישור — ה-API כבר תומך ב-soft delete בכל הישויות (§9.4); רק חסרה כפתור/דיאלוג בצד ה-client.

**שינוי סכימה נדרש (קטן, לא שובר)**: `Child.photoUrl?: string` ב-`packages/contracts` וב-Prisma — אופציונלי, ברירת מחדל `null`. מעלה דרך `POST /media/upload` שכבר בנוי (§14.3, M6) — **אין תשתית חדשה, רק שדה חדש וכפתור העלאה שמפנה לאותו endpoint שהאדמין כבר משתמש בו**.

### 3.3 Games — משחק חופשי (יכולת חדשה, לא קיימת היום)

זה הרעיון המרכזי ממסמך ה-Base44 (בחירת ילד+משחק+רמה, עם/בלי תיעוד) — **ממופה נכון לארכיטקטורה שלנו**:

- מסך חדש: בוחרים ילד (או "תרגול ללא שיוך לילד" — למשחק הדגמה), ואז בוחרים **תת-תחום ספציפי מכל קבוצות הגיל** (לא רק מקבוצת הגיל של הילד — זה ההבדל בין "אבחון" ל"תרגול חופשי": בתרגול מותר לשחק כל תוכן).
- מתג "שמור תוצאה" (ברירת מחדל: כבוי במצב תרגול). כשכבוי — המשחק רץ באותו `GamePlayer` הקיים בדיוק (§17.1, M2), אבל בסיום **לא נכתבת שורת `SubdomainResult`** — הצגת הדירוג בסוף היא ויזואלית-בלבד לילד/גננת, לא מגיעה לשרת. כשמופעל — נכתב סשן עם `mode: PRACTICE` (ראו §3.4) כדי שלא יזהם דוחות אבחון.
- **אין 17 מסכי-משחק נפרדים לבנות** — מסך "משחקים" הוא בעצם עוד כניסה ל-`GamePlayer` הקיים, עם בורר-תוכן שונה (כל תת-התחומים במקום תחום-אחד-שנבחר-מראש). זו תוספת קטנה על גבי §7/§8, לא רכיב חדש.

### 3.4 שינוי נתונים נדרש: `Session.mode`

```prisma
enum SessionMode { ASSESSMENT PRACTICE }
// Session.mode SessionMode @default(ASSESSMENT)
```

כל שלושת הדוחות הקיימים (§12) מסננים `mode: ASSESSMENT` כברירת מחדל — שינוי חד-שורה בכל query קיים ב-`reports` module. מונע בדיוק את מה שהלקוחה לא ביקשה: משחק חופשי "סתם לשחק" שמעוות סטטיסטיקת אבחון אמיתית.

### 3.5 Reports — ליטוש חזותי (ללא שינוי לוגי)

שלושת הדוחות הקיימים (§12) עובדים נכון — M7 רק **מלביש** אותם ברכיבי §2.4:
- `ProgressionReport` — שורת `StatCard` מסכמת מעל הגרף (סה"כ תחומים שנבדקו, תחום חזק ביותר, תחום הכי טעון תיווך).
- `VsGroupReport` — `Avatar` הילד ליד הכותרת.
- `PatternsReport` — עמודות החוזק/קושי (`pattern-col`) מקבלות אייקון וגרדיאנט עדין לפי `--success/--warning/--danger`, במקום פס-צבע-עליון בלבד.
- **הדפסה/PDF**: `ExportPort` (§10.3) כבר בנוי כ-`JsonExportAdapter` (זמני, §17.1). M7 הוא הרגע הטבעי להחליף אותו ב-adapter שמייצר PDF מעוצב (למשל `@react-pdf/renderer` בצד שרת) — **ה-endpoint וה-call site לא משתנים כלל**, זו בדיוק הנקודה שה-port הזה נבנה בשבילה (§3.3).

### 3.6 משטח המשחק — תמונות אמיתיות + חגיגיות

- כל תוכן היום משתמש ב-placeholders (`inline-SVG` + טוני-`tone:` לאודיו — מתועד כמכוון וזמני, §17.1/§18.2). M7 **לא בונה תשתית חדשה** — צינור ההעלאה וה-storage כבר קיימים (M6: `HotspotEditor`, `POST /media/upload`, `STORAGE_DRIVER=r2`). מה שחסר הוא **עבודת תוכן**: איורים בסגנון אחיד (מומלץ, כבר מתועד ב-Spec §8) + הקלטות קול אנושיות — זו עבודה הוצאתית (מאיירת/קריינית), לא פיתוח.
- **פידבק חזותי מוגבר**: `ConfettiBurst` + `MascotBubble` על תשובה נכונה; רטט-עדין (CSS `animation: shake`) על תשובה שגויה — משדרג את `.feedback.correct/.wrong` הקיים ב-`app.css` (§204-218) בלי לגעת בלוגיקה של ה-state machine (§8, שנשארת נטולת-UI לגמרי לפי עיקרון §3.6).

### 3.7 מסך התחברות — ליטוש (`.login-screen`)

`LoginScreen.tsx` (M3) היה כרטיס יחיד על רקע ריק. **מומש**: אותו טופס בדיוק (`login()`, אותם שדות, אותה ברירת-מחדל לדמו) בתוך `.login-screen` — רקע `--gradient-soft` + שני "בועות" דקורטיביות, וכרטיס צף (`.login-panel`, `--shadow-float`) עם סימן-מותג (`--gradient-hero`) עקבי לזה שמופיע בסיידבר (§3.8). **אין שינוי התנהגותי** — זו החלפת CSS/מבנה בלבד, לא לוגיקת אימות חדשה.

נשקל ונדחה: מסך "מחולק" (split-screen, פאנל מותג בצד) כמקובל ב-SaaS דסקטופי. **לא מתאים כאן** — המכשיר העיקרי הוא iPad לרוחב/לאורך (§2 ב-Spec), וחלוקה דו-טורית לרוב "נשברת" או משאירה חצי-מסך ריק בפורטרט. כרטיס ממורכז מלא מכל גודל מסך.

### 3.8 מעטפת גננת — סיידבר + טופבר (`AppShell`)

לפני M7 כל מסך (`HomeScreen`, `RosterScreen`, `ReportsScreen`) צייר לעצמו כותרת+ניווט-חזרה+כפתור-יציאה נפרדים (`PageHeader` חוזר עם props שונים בכל מסך) — עבד, אך לא הרגיש כמו אפליקציה אחת. **מומש**: רכיב `AppShell` יחיד ב-`packages/ui` (markup-בלבד, כמו כל רכיב §2.4 אחר) שמלביש **רק** את שלושת מסכי העיון/ניהול (בית / ילדים / דוחות) בסיידבר קבוע (סימן-מותג, ניווט בין השלושה, כרטיס-משתמש+יציאה בתחתית) וטופבר (כותרת עמוד דינמית, תג סנכרון-Outbox חי מ-`useOutbox()` הקיים, כפתור "+ אבחון חדש").

**החלטה מכוונת שנשמרת מ-M3/M4/M5/M6**: משטח המשחק (`SessionRunner` וגם מצב `PracticeScreen` כשהוא ב-שלב 'playing'/'done') **נשאר מחוץ למעטפת לגמרי** — בדיוק כפי ש-`App.tsx` כבר החזיר את `SessionRunner` לפני מיתוג ה-view עוד מ-M3. הסיבה זהה לזו שמתועדת ב-§11.2 של HIGH-LEVEL-DESIGN: ברגע שהילד יושב מול האייפד, שום ניווט — אפילו סיידבר יפה — לא אמור להיות נגיש לו. `PracticeScreen` בשלב ה-setup (בחירת ילד/תחום) גם הוא נשאר מחוץ למעטפת, מאותה סיבה בדיוק: יכול להיות שהילד כבר יושב ליד הגננת בזמן הבחירה.

**עדיין בלי ראוטר** — שלוש views (לא חמש כפי שדמיינתי במקור לפני המימוש) ב-state מקומי הן עדיין הדבר הפשוט ביותר שעובד בהיקף הזה; זו אותה החלטה שנדחתה שוב ב-M3/M4/M5/M6 (§11.1 ב-HIGH-LEVEL-DESIGN), לא נסיגה.

## 6. מה נשאר זהה (ולמה זה טוב)

- ה-state machine של הסשן (§8), טקסונומיית המשחקים (§7), מודל הנתונים (§9), וה-RBAC (§13) — **לא זזים**. M7 הוא כולו שכבת תצוגה + כמה שדות תוספתיים.
- זרימת האבחון (בחירת ילד → תחום → משחק → דירוג גננת → 3 ניסיונות → הערה בכישלון) נשארת **בדיוק** כפי שהלקוחה תיארה במסמך המקור — שום דבר ב-M7 נוגע בה.
- העקרון "תוכן זה נתון, לא קוד" (§3.1) הוא הסיבה שמצב-משחק-חופשי (§3.3) ותמונות אמיתיות (§3.6) לא דורשים ארכיטקטורה חדשה — הן צורכות בדיוק את מה שכבר נבנה.
